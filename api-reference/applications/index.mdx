---
title: "Applications API"
description: "Manage the unified Applications spine and its OAuth, rewards, and subscriptions capabilities."
---

In mgPass v3, every integration is a single `applications` row (the **spine**) with zero or more **capability** rows attached: OAuth, rewards, and subscriptions. The legacy `oauth_clients`, `rewards_partners`, and `subscription_tenants` tables are gone — one `application_id` flows end-to-end through the platform, including outbound webhooks.

A capability is present when its row exists. Enabling a capability inserts the row; disabling it deletes the row. Secrets (`client_secret`, `api_key`, webhook `secret`) are returned exactly **once** at create or rotate time — we store hashes (bcrypt for OAuth client secrets, SHA-256 for rewards/subscriptions API keys) and the raw HMAC for webhook signing.

All endpoints below require an admin bearer token. Use the `applications:read` scope for `GET` calls and `applications:write` for everything else. For the conceptual walkthrough — when to enable each capability, naming conventions, and the relationship to organizations — see the [Applications guide](/guides/applications).

## Webhooks

One application can have many webhooks. Each webhook subscribes to a chosen set of event types across every enabled capability and is signed with its own raw HMAC `secret`. See the [Webhooks guide](/guides/webhooks) for signature verification and the full event catalog.

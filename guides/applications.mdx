## What is an Application in v3?

An **Application** is a single row in the `applications` table representing a customer-facing integration with mgPass. 3News, mgTix, adesa+ — each is one Application. The row carries the integration's identity: id, slug, display name, description, logo, support email, branding, and (optionally) the organization it belongs to.

An Application on its own does nothing. What it does is determined by the **capabilities** attached to it. There are three capabilities today — OAuth, Rewards, and Subscriptions — and each is a separate 1:1 row that hangs off the Application spine. An Application can have one capability, two, all three, or none.

<Note>
In earlier versions of mgPass, OAuth clients, rewards partners, and subscription tenants were three separate entities with three separate ID spaces (`client_id`, `partner_id`, `tenant_id`). In v3 they are all the same thing: an Application. There is one ID — `application_id` — that flows end-to-end through the database, API responses, admin views, and webhook payloads. See [Migration from legacy entity names](#migration-from-legacy-entity-names) at the bottom of this page if you're updating older integration code.
</Note>

## The three capabilities

A capability is a row attached to an Application by `application_id` (primary key + foreign key in one). **Presence of the row means the capability is enabled.** There is no boolean flag — enabling a capability inserts the row, disabling it deletes the row.

    Lets users sign in to your service using mgPass identity. Standard OAuth 2.1 / OIDC: authorization code + PKCE, refresh tokens, userinfo, logout. Carries `client_secret_hash` (bcrypt), `redirect_uris`, `post_logout_uris`, `allowed_scopes`, `cors_origins`, token TTLs, refresh token rotation, allowed auth methods, access control rules, and optional `custom_domain`.
  </Card>
  <Card title="Rewards" icon="gift" href="/guides/awarding-points">

  </Card>

    Lets your service sell recurring plans through mgPass — checkout, billing, entitlements, dunning, all handled. Carries `api_key_hash` (SHA-256), `billing_email`, `entitlement_jwt_mode`, `notification_config`, and `allowed_widget_origins` for the embeddable widget.
  </Card>

## Why one spine instead of per-capability tables

Folding OAuth clients, rewards partners, and subscription tenants into a single Application spine gives a few concrete properties:

- **One ID end-to-end.** `application_id` is the same value in the database, the console URL, the API response JSON, the webhook payload, and the OAuth `client_id` flow parameter. No translation layer, no joins to bridge "the OAuth client for this rewards partner."
- **Combined integrations are free.** A partner that signs users in *and* sells subscriptions *and* awards points is one Application with three capability rows. Branding, support contact, organization assignment, and webhook config are shared automatically.
- **Adding capabilities later is cheap.** A new capability is one new table keyed on `application_id` — no schema-wide migration, no backfill, no admin UI rewrite.
- **Webhooks are unified.** An Application has N webhook endpoints, and each endpoint can subscribe to events from any of the capabilities the Application has enabled. You don't configure webhooks per capability; you configure them per Application and pick the event types.
- **The OAuth `client_id` *is* the `application_id`.** When a browser hits `/authorize?client_id=app_abc123`, that's the Application spine row. No lookup table.

## Anatomy of an Application row

The spine carries identity fields only. Everything operational lives on capability rows.

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | `app_*` identifier. Used as `client_id` in OAuth flows and `application_id` everywhere else. |
| `slug` | string | URL-safe short name (`3news`, `mgtix`). Unique. Used in console URLs and as a stable handle. |
| `name` | string | Display name shown on consent screens, checkout, emails. |
| `description` | string \| null | Optional one-liner shown on the consent screen. |
| `logo_url` | string \| null | Public URL to the Application's logo. Rendered on consent, checkout, and notification surfaces. |
| `support_email` | string \| null | User-facing support address. Shown on billing emails and error pages when set. |
| `branding` | object \| null | Per-Application color/theme overrides. JSON: `{ primary_color, accent_color, ... }`. |
| `organization_id` | string \| null | Optional FK to `organizations`. Groups Applications under a parent partner/enterprise. |
| `is_active` | boolean | Soft enable/disable for the whole Application. Disabling blocks OAuth, rewards events, and checkout sessions across all capabilities. |
| `created_at` | timestamp | |
| `updated_at` | timestamp | |

## Enabling a capability

You can enable a capability from the developer console or directly via the management API. Both flows return the secret/api key **once** — there is no way to retrieve it later, only rotate.

<Steps>
  <Step title="Create the Application">
    In the developer console, go to **Applications → New Application**. Fill in name, slug, optional logo/branding, optional organization. Save. At this point you have a spine row with zero capabilities — useful as a placeholder, but it can't do anything yet.

    Equivalent API call: `POST /api/applications` — see [Create application](/api-reference/applications/create-application).
  </Step>
  <Step title="Open the Application detail page">
    Click into the new Application. You'll see three capability cards — OAuth, Rewards, Subscriptions — each with an **Enable** button.
  </Step>
  <Step title="Enable the capability you need">
    Click **Enable** on the capability card. Fill in the capability-specific fields:

    - **OAuth**: `client_type` (web / spa / native / m2m), `redirect_uris`, `post_logout_uris`, `allowed_scopes`, `cors_origins`, optional `custom_domain`.
    - **Rewards**: `allowed_event_types` (which event slugs this Application is permitted to publish), `points_multiplier`, optional `custom_rules`.
    - **Subscriptions**: `billing_email`, `entitlement_jwt_mode` (`embedded` or `none`), `allowed_widget_origins` (origins permitted to embed the checkout widget).

    Equivalent API calls:
    - `POST /api/applications/:id/capabilities/oauth` — see [Enable OAuth capability](/api-reference/applications/enable-oauth-capability)
    - `POST /api/applications/:id/capabilities/rewards` — see [Enable Rewards capability](/api-reference/applications/enable-rewards-capability)
    - `POST /api/applications/:id/capabilities/subscriptions` — see [Enable Subscriptions capability](/api-reference/applications/enable-subscriptions-capability)
  </Step>
  <Step title="Copy the secret">
    On enable, the response returns the secret material (OAuth `client_secret` or Rewards/Subscriptions `api_key`) in plaintext exactly once.

    <Warning>
    The secret is shown **only once** at enable time. mgPass stores only the hash — bcrypt for OAuth client secrets, SHA-256 for Rewards/Subscriptions api keys. If you lose the secret, you must rotate it; there is no recovery.
    </Warning>

    Store it in your deployment's environment variables or secret manager immediately.
  </Step>
  <Step title="Add more capabilities later if needed">
    Capabilities are independent. You can ship with OAuth only, then come back months later and enable Subscriptions on the same Application — branding, name, organization, and webhooks all carry across automatically.
  </Step>
</Steps>

To disable a capability, delete its row: **Disable** in the developer console, or `DELETE /api/applications/:id/capabilities/<oauth|rewards|subscriptions>`. The spine row stays intact. Re-enabling later generates a fresh secret.

## Secrets and rotation

There are three kinds of secret material associated with an Application, stored three different ways for three different reasons.

| Secret | Where it lives | Storage | How to rotate |
|--------|---------------|---------|---------------|
| OAuth `client_secret` | `application_oauth.client_secret_hash` | bcrypt | `POST /api/applications/:id/capabilities/oauth/rotate-secret` |
| Rewards `api_key` | `application_rewards.api_key_hash` | SHA-256 | `POST /api/applications/:id/capabilities/rewards/rotate-key` |
| Subscriptions `api_key` | `application_subscriptions.api_key_hash` | SHA-256 | `POST /api/applications/:id/capabilities/subscriptions/rotate-key` |
| Webhook `webhook_secret` | `webhooks.webhook_secret` | **raw** (not hashed) | `POST /api/applications/:id/webhooks/:webhook_id/rotate-secret` |

Why webhook secrets are stored raw: mgPass *signs* outbound webhook payloads with HMAC-SHA256, which means the server needs the original secret to compute the signature on every delivery. Hashing it would make signing impossible. OAuth client secrets and API keys, by contrast, are only *verified* on inbound calls (constant-time compare against the hash), so hashing is the correct choice there.

<Warning>
Rotation is immediate. The old secret stops working the moment the rotation endpoint returns. There is no grace period and no dual-secret window. Plan your deployment so the new secret is in place before you rotate — typically: write the new secret to your secret manager, redeploy your service, then call the rotation endpoint and discard the old one.
</Warning>

- [Rotate Rewards API key](/api-reference/applications/rotate-rewards-key)

## Webhooks per Application

Webhooks attach to the Application, not to individual capabilities. One Application can register many webhook endpoints — different URLs for different teams, or one URL that filters server-side. Each webhook subscribes to a list of `event_types`, and those event types can come from any capability the Application has enabled:

- **Subscriptions** events: `subscription.created`, `subscription.activated`, `subscription.renewed`, `subscription.payment_failed`, `subscription.unpaid`, `subscription.cancelled`, `subscription.expired`, `subscription.trial_ending`, `subscription.plan_changed`.
- **Application** lifecycle events: `application.created`, `application.updated`, `application.capability_enabled`, `application.capability_disabled` (useful for monitoring).
- Additional event families ship with their respective capabilities — see the [Webhooks guide](/guides/webhooks) for the full catalog and HMAC verification recipe.

Every delivery is logged in the shared `webhook_deliveries` table — same log for all capabilities, queryable by `application_id` and `webhook_id`.

Manage webhooks via:

- [Create webhook](/api-reference/applications/create-webhook)
- [List webhooks](/api-reference/applications/list-webhooks)
- [Update webhook](/api-reference/applications/update-webhook)
- [Delete webhook](/api-reference/applications/delete-webhook)

## Custom domains and subdomains

The OAuth capability supports serving the authorize, token, userinfo, and logout endpoints from a domain you control — e.g. `auth.yourdomain.com` instead of `auth.mgpass.net`. This lets users see your brand in the URL bar during the login redirect.

Set `application_oauth.custom_domain` (and optionally `custom_subdomain` for a subdomain of `mgpass.net`) when enabling or updating the OAuth capability. mgPass terminates TLS for the custom domain; you point a CNAME at the value we give you and we handle certificates.

Custom domains apply **only** to OAuth endpoints. Rewards and Subscriptions APIs always live at `auth.mgpass.net`, and hosted checkout always lives at `pay.mgpass.net`.

## Organizations

An Application can belong to an **Organization** (`applications.organization_id`). Organizations group Applications under a single parent — a media group with three OAuth-enabled news sites, or an enterprise with separate Applications for staff vs. customer flows. Organization-scoped admins can manage all the Applications underneath without root admin rights.

See the [Organizations guide](/guides/organizations) for the full multi-tenant model.

## Migration from legacy entity names

If you're updating an integration that predates v3, you'll have seen one or more of these column or field names. They're all the same thing now:

| Legacy name | v3 name | Notes |
|-------------|---------|-------|
| `client_id` (OAuth) | `application_id` | The public OAuth `client_id` flow parameter still exists and is **equal to** `application_id`. No translation needed on either side. |
| `tenant_id` (Subscriptions) | `application_id` | The Subscriptions tenant table is gone. Wherever you used to send `tenant_id`, send `application_id`. |
| `partner_id` (Rewards) | `application_id` | Rewards partner records are gone. The `X-API-Key` you hold maps to one `application_id`. |
| `oauth_clients` (table) | `applications` + `application_oauth` | The spine row holds identity/branding; the capability row holds OAuth config. |
| `rewards_partners` (table) | `applications` + `application_rewards` | Same split. |
| `subscription_tenants` (table) | `applications` + `application_subscriptions` | Same split. |
| `/api/clients/*` (admin endpoints) | `/api/applications/*` | All management endpoints moved. The old paths return 404. |

Webhook payloads emitted from v3 use `application_id` exclusively. If you wrote a verifier against an older payload that read `tenant_id` or `partner_id`, update the field name — the value will be the same `app_*` identifier.

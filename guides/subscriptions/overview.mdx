## What the engine does

The mgPass Subscriptions Engine turns any registered [Application](/guides/applications) into a recurring-revenue product. It handles plan management, hosted and embedded checkout, card billing through Paystack, dunning, multi-seat subscriptions, sponsored grants, and pushes every state change to your backend as a webhook and into your access tokens as a JWT claim.

You configure plans and pricing once; the engine handles the recurring side end-to-end — first charge, scheduled renewals, retries, cancellations, and reactivations.

## Lifecycle at a glance

Every subscription moves through a fixed state machine:

```
                 ┌──────────┐
   new sub ────▶ │ trialing │ ──── trial ends ────┐
                 └──────────┘                     ▼
                                          ┌────────────┐
                 new sub (no trial) ────▶ │   active   │ ◀── reactivate ──┐
                                          └────────────┘                  │
                                                │                         │
                                       payment fails                      │
                                                ▼                         │
                                          ┌────────────┐                  │
                                          │  past_due  │ ── retries ──────┤
                                          └────────────┘                  │
                                                │                         │
                                       retries exhausted                  │
                                                ▼                         │
                                          ┌────────────┐                  │
                                          │   unpaid   │ ─────────────────┘
                                          └────────────┘
                                                │
                                       grace period over
                                                ▼
                                       ┌─────────────────┐
                                       │ cancelled /     │
                                       │ expired         │
                                       └─────────────────┘
```

A separate `paused` status exists for manually-suspended and sponsored-only flows. See [Lifecycle](/guides/subscriptions/lifecycle) for the full state diagram, transitions, and retry schedule.

## The Application spine

Every subscription belongs to an [Application](/guides/applications) via `application_id`. The Application is the long-lived spine; subscription billing is a **capability** attached to that spine via the `application_subscriptions` row.

Before you can sell anything, an admin enables the Subscriptions capability on the Application (in the admin console or via API). That action:

1. Inserts the capability row.
2. Generates an `X-API-Key` your backend uses to call `/v1/*` endpoints.
3. Lets you start creating plans and checkout sessions under that `application_id`.

The same `application_id` flows through plans, checkout sessions, subscriptions, payments, invoices, webhooks, and JWT entitlement claims. If you ever see `tenant_id` or `subscription_tenant_id` in old code or notes, that's pre-v3 — read [Applications](/guides/applications) for the current model.

## JWT entitlements

When a user logs in to an Application, their `access_token` carries a `subscriptions` claim derived from their active (or trialing) subscriptions for that Application. Your backend can authorize feature access without making a round trip to mgPass.

Two modes, configured per Application on `application_subscriptions.entitlement_jwt_mode`:

<Tabs>
  <Tab title="plan_status (default)">
    Compact. Just the plan slug and status — enough for "do they have any paid plan."

    ```json
    {
      "sub": "usr_abc123",
      "subscriptions": [
        { "plan": "pro_monthly", "status": "active" }
      ]
    }
    ```
  </Tab>
  <Tab title="full_features">
    Includes the `features` array from the plan, so you can gate individual feature flags from the token alone.

    ```json
    {
      "sub": "usr_abc123",
      "subscriptions": [
        {
          "plan": "pro_monthly",
          "status": "active",
          "features": ["unlimited_articles", "no_ads", "early_access"]
        }
      ]
    }
    ```
  </Tab>
</Tabs>

The claim refreshes on every token issue and on every `/oauth/token` refresh, so state changes (cancel, upgrade, payment failure) propagate within one token TTL. For instant invalidation, query the entitlement API directly — see the [API reference](/api-reference) for `GET /v1/entitlements/:user_id`.

## Billing rails

| Rail | Status | Notes |
|---|---|---|
| Paystack — card | Shipped | Recurring authorization via Paystack tokenization. Used for all monthly/annual card subscriptions. |
| Paystack — bank | Shipped | One-off bank charges through Paystack checkout. |
| Hubtel — mobile money (one-off) | Shipped | First charges only; recurring deferred. |
| Hubtel — MoMo Repeat Payments | **Deferred** | Awaiting Hubtel v1.2 spec. Mobile money plans can't auto-renew yet — they fall back to manual reactivation. |

The card-only rule has one hard-coded gate today: an `interval: "annual"` plan cannot be paid with `payment_provider: "hubtel"`. See [Currency & billing rails](/guides/subscriptions/currency) for the full matrix.
